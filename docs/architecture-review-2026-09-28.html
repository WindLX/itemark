Problem

「一条记录是否已完成」有两套判定：show/list 读 kind 中名为 status 的字段， 而 summary 按 completion_field 归类并自行硬编码四个状态名；完成依据的门槛在 checks.rs 里也写了两遍， 于是同一条记录在 show --json 与 summary --json 里可以给出不同的业务状态。

Solution

让一个模块从「记录 + kind」算出唯一的业务状态与完成依据缺口——是否处于完成值、缺完成说明还是缺证据、还是已显式标注未验证——五个调用点都读这一个结果。

Benefits

  • locality：业务状态规则只改一处
  • leverage：5 个调用点共用一次判定
  • locality：完成门槛不再写两遍
  • tests：show 与 summary 的状态可对账
  • 删除测试：删掉重复判定，复杂性集中而非搬走
  • 术语：业务状态 与 完成依据 各归一位
与既有决定的关系： docs/design.md 与 docs/cli.md 明确写出字段名、配置键与状态名仍是工程草案，因此把业务状态收敛到一处不重开任何已定决策； 唯一需要重新挑选的是「事实的核实状态」如何由 kind 表达，这也是 CONTEXT.md 尚未定稿的部分。
