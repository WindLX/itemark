# CLI 交互草案

> 状态：已确认行为的接口草案。CLI 尚未实现；命令参数、字段名和文件路径是讨论用示例，不是已交付行为。

Worklog 是本地 Rust + Clap 同步 CLI。每个 kind 由项目配置和 Markdown 模板定义；用户可增加 kind，不由程序固定为 `work`、`fact`、`term` 三类。模板可声明字段及少量约束（必填、基础类型、枚举）和必填正文节；不支持脚本或任意工作流规则。

## 配置、呈现和校验

- 取值顺序：显式 CLI 参数 → 项目 `worklog.toml` → 内置默认值。不预设全局配置或完整环境变量合并层。
- 项目配置中的 `root` 指定 Worklog 根目录；推荐相对 `worklog.toml` 所在目录解析。`kind.template` 指向根目录中的本地 Markdown 文件；相对路径推荐相对 Worklog 根目录解析，与进程当前目录无关。这些路径规则是工程草案。
- 仓库默认人读界面为简体中文，项目配置可声明 `language = "zh-CN"`。该设置只选择 CLI 固定提示和摘要模板的语言，不改写既有 Markdown 或翻译用户内容；程序不推断正文语言，也不内置翻译服务。
- 命令、字段、状态机器值、ID 和 JSON 键保持稳定，不翻译。语言切换不改变字段键或必填正文节的匹配规则。自然语言正文由用户或 AI 撰写；AI 遵循仓库 `AGENTS.md` 的语言偏好。
- 所有命令默认输出面向人的文本；可选 JSON 呈现，同一命令行为不变。错误返回非零退出状态。
- 每次查询都从当前 Markdown 记录构建索引，不使用数据库或持久查询缓存。
- `add` 可写入尚未填完的记录，不增加 `draft` 状态。它检查已提供的值及记录结构；只有非空字段才做类型/枚举校验。
- `check` 报告缺失或为空的必填字段和正文节，并检查 ID、引用及适用的完成条件。普通写入不触发全量检查，但要保住记录可解析、ID 唯一性和引用完整性。
- 精确的配置键、基础类型集合、模板语法和字段位置仍待定；kind 只由配置定义，不在 CLI 中写死。

## 命令草案

下表列出已确认的操作职责。命令拼写以便阅读为主，选项和参数形式尚未冻结。

| 命令 | 行为 |
| --- | --- |
| `init` | 初始化项目配置和推荐目录；是否写入 kind/group 种子数据仍属草案。 |
| `add` | 按指定 kind 添加记录；可暂缺必填内容，稳定 ID 由 Worklog 分配。 |
| `show` | 按稳定 ID 查看一条记录。 |
| `list` | 列出记录，可按 kind、状态或 group 过滤。 |
| `search` | 搜索当前记录内容；引用通过稳定 ID 跨 group 指向原记录。 |
| `update` | 定点更新字段或指定正文节；也可移动记录到另一个 group。 |
| `log` | 即时追加一条带日期的进展记录。 |
| `drop` / `restore` | 废弃或恢复任一 kind 的记录；恢复保留废弃前的业务状态。 |
| `group list/add/show` | 查看、新建或查看一级 group；group 可包含不同 kind。 |
| `kind list/show/check` | 查看并检查项目配置中的 kind；不提供逐字段 schema 编辑器。 |
| `check` | 检查记录必填项、正文节、关系及适用的完成条件。 |
| `summary` | 生成当前总览或交接，注明来源 ID 和生成时点；默认只输出，显式指定保存位置后才写文件。 |

## 记录行为

记录采用 YAML 头部和 Markdown 正文。`update` 只改指定字段或正文节，保留其余正文；不承诺 YAML 原文顺序或空白的逐字往返。每条记录恰属一个一级 group；group 可混合 kind，不嵌套。移动改变归属但不改变稳定 ID，引用按 ID 工作，不复制被引用内容。

业务状态由 kind 决定。工作事项使用 `todo`、`in_progress`、`blocked`、`done`；事实的核实状态可按其 kind 定义，术语不要求业务状态。`drop` / `restore` 是独立的通用记录生命周期，不能替代业务状态。

kind 可选地声明一个完成字段及完成值。仅当该映射已声明、且写入值匹配完成值时，CLI 要求非空的统一完成说明，以及证据引用或明确的未验证说明。`check` 对所有记录应用同一条件；未声明映射的 kind 不应用此规则。具体配置键和完成元数据的存放位置仍是草案。

## 典型操作

1. `init` 建立项目；根据 `worklog.toml` 中的 `work` 示例添加一条工作事项，并用 `show` 读回。
2. 用 `group add` 建立一级 group，把同组的工作事项、事实和术语分别加入；用 `list`、`search` 查找，并以 ID 互相引用。
3. 用 `update` 改标题、配置字段或一个正文节，或将记录移动到另一 group；用 `log` 追加进展。未触碰的 Markdown 正文继续保留。
4. 用 `drop` 暂停记录，之后 `restore` 回到原业务状态；用 `check` 查看尚缺的必填信息。
5. 用 `summary` 在 stdout 查看交接；只有明确要求保存时才传入保存位置。用 `--json` 可把同一结果交给脚本读取。

这些场景描述目标行为，尚未在 CLI 中执行。记录的权威来源是 Markdown 文件；总览和交接由当前文件生成，不构成第二份状态。语言设置只影响 CLI 固定文案，不会更改模板创建后的用户正文。

建议的新项目布局为 `worklog.toml`、`<root>/items/`、`<root>/templates/` 和 `<root>/summaries/`。这是布局建议，不要求将当前手工 v0 的 `docs/worklog/` 自动迁移。
